# 问题陈述

同一套程序与配置在使用者的机器上会存在多处可运行、可编辑的副本，使用者无法在不加判断的情况下知道"哪一份程序在生效、哪一份配置是我正在编辑的"；同时现版本的升级流程需要在使用者机器上现场生成新程序，把这份不确定性又扩散到升级之后。当使用者想把下载来的文件清理掉时，他会要么失去方便的配置入口，要么必须长期承担多份副本之间版本与内容是否一致的判断。

# 受影响的使用者与相关方

- **使用者：项目维护者本人** — 他的机器上同时存在下载区与安装区两份程序、两份配置；他需要判断当前生效的是哪一份，并处理两边是否一致。— [source: intake.md、research.md]
- **使用者：被分发的少量朋友** — 他们的机器没有编译条件，只能接收预编译程序；安装与每次升级都需要他们手动完成一串步骤。— [source: research.md（来源为维护者口述，confidence: medium）]
- **相关方：维护者（决策者与出资方）** — 由他决定是否为了更好的安装体验接受额外成本（例如年度签名费用与发布流程改造）。— [source: intake.md]
- **相关方：未来的使用者** — 会直接承受安装形态带来的步骤数、权限要求与系统能力差异；目前没有反馈渠道可以量化他们的诉求。— [source: research.md]

# 目标

- 使用者在安装完成后，只存在一份生效中的程序与一份生效中的配置，不需要判断"我在编辑哪一份"。
- 使用者可以安全地清理下载来的文件，并且仍然能方便地再次进入配置与状态查看。
- 升级不需要使用者机器具备开发工具，也不会在使用者机器上重新生成程序。
- 在任何安装形态变更进入实施之前，其对使用者的可见影响与对系统能力的影响已被逐条列出，并且明确区分"已验证"与"未验证"，避免重复"实施完成后才发现能力缺失"的路径。

# 非目标

- 不改变网络识别与挂载逻辑本身（这一部分已单独处理）。
- 不建设跨平台支持，范围仍是 macOS 27 及以上的 Apple silicon 设备。
- 不把"使用者必须先安装第三方包管理器"作为方案前提。
- 不改变凭据处理方式（凭据继续由系统钥匙串管理）。
- 不新增常驻的第二个运行进程，也不增加图形界面。

# 成功指标

- 安装后删除下载来的文件，仍能通过一个稳定入口进入配置与状态查看。（基线：安装目录中的程序不在系统默认搜索路径内，只能手动输入长路径）
- 安装与升级完成后，生效中的程序副本数量为 1、生效中的配置副本数量为 1。（基线：存在两处可运行程序与两处可编辑配置）
- 在没有开发工具的干净环境里可以完成升级。（基线：现版本升级需要本机编译）
- 卸载后不留下后台服务、服务描述文件与安装目录。（基线：现有卸载流程已能做到，作为不退化指标）
- 变更进入实施前，评审文档能逐条给出使用者可见影响与系统能力影响，并标注验证状态。（基线：上一次分发形态变更在实施完成后才发现丢失了网络变化触发能力）
- 在不购买签名服务的前提下，所选形态仍能提供当前网络识别所需的平台能力；若不能，必须给出使用者可见后果与替代方式。（基线：未签名程序在本机读不到网关 MAC，已实测）
- 维护者对"现在生效的是哪一份"不再需要人工确认。（定性指标，无基线数据）

# 不行动的代价

维护者每次发版仍要处理两处程序与两处配置的同步；被分发者每次升级都要重新执行一遍安装步骤；升级流程继续要求使用者机器具备开发工具，与本项目自身原则相冲突；使用者在清理下载文件后仍缺少方便的配置入口；下一次安装形态变更仍然可能在实施完成后才暴露代价，重复已经发生过一次的返工。

# 已确认的边界条件（维护者决定，2026-10-02）

- 允许一次管理员授权：安装过程中可以要求使用者输入一次密码。
- 允许安装器自行修改使用者的 shell 配置；不得要求使用者手工修改；卸载时必须把该修改还原。
- 不接受每年 99 美元的签名费用，因此不把开发者签名与公证作为方案前提。
- 升级必须由程序自行完成，且使用者机器上不需要任何编译工具。
- "未签名程序读不到网关 MAC"纳入本次评估范围，不作为边界外事项记录。

# 由上述决定产生的新问题

- 与项目宪法的潜在冲突（已部分化解）：宪法在项目约束中写明后台服务"不需要 Root 权限"，其原始意图是避免每次运行或每次配置都要求输入密码，而不是禁止一次性授权。维护者已授权在确有必要时把这条约束从项目级降为本次评估的边界条件。当前实测已确认存在"不需要 root、也不需要签名"的可行路径，因此该冲突未必发生；若后续阶段确认方案必须依赖 root 组件，再据此修改宪法约束。
- 不允许付费签名与公证的前提下，使用者首次运行的体验取决于"未验证"的拦截行为；若直接从终端安装而不是双击图形界面，按本机实测不会被拦。分发形态需要在结论中明确使用者实际走的路径。
