# 想法（原样记录）

> 在新建 feature 前，我们先进行一个 idea 的摸索。注意进入 SDD。
>
> 之前我想引入 Homebrew，是因为不想永远有程序区和系统区两套程序、两套配置文件。这样会导致几个问题：
> 第一，如果我删除程序区的程序和配置文件，我就没法去配置程序了；
> 第二，如果我留着程序区的程序和配置文件，就永远有两边版本是否一致、配置文件版本是否一致，互相之间如何同步的混乱。
>
> 现在看起来，如果 Homebrew 的代价比较大，那么，到底应该用什么安装方式？才能让用户不需要先把程序下载到本地、先运行、配置安装守护程序、再删掉之前下载的程序。这些安装方法是否都会有各种各样的代价，我尽量不想像 Homebrew 那样做到最后发现有无法监听网络变化的代价这样类似的事情发生。
>
> 如果这些方法都不好，那么退而求其次，我也能接受先把程序下载到本地、先运行、配置安装守护程序、再删掉之前下载的程序。这样的话，是否必须为程序注册 PATH，才能方便后续运行配置？

# 重述

维护者希望重新确定 AutoMount 的分发与安装方式，以及安装完成后的程序调用入口；目标是彻底消除"程序区与系统区各一份程序、各一份配置"的状态，并且不接受在实施完成后才发现类似"网络变化监听能力丢失"的隐藏代价。如果不存在更好的做法，维护者可以接受"下载 → 运行 → 完成配置并安装守护程序 → 删除下载的文件"这一基本形态，同时需要判断是否必须注册 PATH 才能方便后续再次进入配置。

# 来源与背景

- **提出者**：项目维护者本人（不写代码，熟悉产品逻辑与常见技术概念）
- **触发事件**：2026-10-02 的会话中，维护者决定回滚此前已推送的 Homebrew 改造。回滚原因之一是该改造把服务定义交给 Homebrew 后，后台服务只剩周期触发，失去了原有"网络配置变化即触发"的能力，而这个代价是在改造基本完成之后才被发现的。回滚后仓库与产品状态已回到 v2.7.4。
- **相关既有事实**（本次会话中已核实，供后续阶段参考，不代表结论）：
  - 现版本的配置路径跟随"当前运行的可执行文件所在目录"，因此从下载目录运行和从安装目录运行会读到不同的配置。
  - 现版本的安装会把程序、源码与配置三份文件复制到用户的 Application Support 目录，形成两份程序、两份配置。
  - 现版本的自更新会下载源码并在用户机器上用编译工具现场编译，然后把下载区与安装区两边同步。
  - 官方包管理器生成的服务定义无法表达"网络配置变化"触发。
