# 核心原则

## I. 配置数据只能来自真实探测或使用者的明确输入

程序不得在源码、交互默认值或回退逻辑中写入特定用户环境的地址、主机名、共享路径或用户名。所有配置值只能来自运行期的真实探测或使用者的明确输入。开发与验证过程不得手工伪造业务配置：配置必须由程序自身的初始化与配置功能生成。凭据不得写入配置文件或日志。

## II. 不得引入第二个常驻运行进程

程序的后台评估必须由系统提供的服务机制按需启动，不得为实现同一目的再引入一个常驻等待进程，也不得让配置入口与后台服务各自维护独立的运行循环。

## III. 每个用户配置只有一个活动来源

后台服务与交互入口必须读取同一份活动配置；迁移不得造成多份可独立编辑的活动配置长期并存。迁移的具体交互方式由对应的 Feature 规格决定。

## IV. 版本与发布产物必须来自同一真理来源

程序版本只在一处维护。配置中的版本、命令输出、发布 Tag 与发布标题必须与该值一致；正式发布物必须与源码版本一致，不得出现二者脱节。

# 项目约束

## 凭据

SMB 凭据由系统钥匙串管理；程序不得把密码写入配置文件或日志。

# 治理

本 Constitution 只承载持久工程原则；产品决策由 Feature 规格承担，流程与发布规则由项目根 AGENTS.md 承担，避免宪法条款与产品决策的变更相互干扰。修改本文件时必须说明变更范围与理由，并按 SemVer 规则递增版本。产品、安全、隐私、数据保留与发布决定必须由维护者明确给出或标为待确认，不得用未声明的行业默认值替代。
