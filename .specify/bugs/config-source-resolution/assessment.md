# 现象报告

工作区配置和 Application Support 守护配置可能分别缺失、可用、内容损坏、版本高于当前程序，或因文件系统错误而不可读。现有三个命令对这些状态采用不同且不完整的判断，导致有效配置未被用于恢复，或初始化操作可能覆盖现有配置。

# 症状

当 LaunchAgent 已安装、守护配置文件存在但无法解码时，`--config` 仍选择该文件并退出，没有使用有效的工作区配置。`--install` 将损坏和未来版本配置都归为无效守护配置，即使工作区配置有效也会中止；两边都不可用时不会从安装命令进入初始化向导。`--init` 只检查工作区文件并可能全量重写它，不检查守护配置。

# 复现

1. 让 LaunchAgent 配置路径存在，守护 plist 内容损坏，并确保工作区配置可读取且版本可迁移。
2. 运行 `./auto_mount --config`：当前代码因优先选择存在的守护文件而无法进入管理菜单。
3. 运行 `./auto_mount --install`：当前状态解析返回 `.invalidRuntime`，要求用户另行显式选择工作区配置；如果两个配置都不可用，安装也不会启动配置向导。

## 涉及代码

- `auto_mount.swift:83` — `preferredManagementConfigURL` 只检查 LaunchAgent 和运行配置文件是否存在，不检查配置是否可读。
- `auto_mount.swift:1523` — `runInitWizard` 只提示并可能全量覆盖工作区配置，没有初始化前状态解析或备份。
- `auto_mount.swift:2574` — `manageConfiguration` 基于文件存在选择运行配置，加载失败就退出。
- `auto_mount.swift:2766` — 安装来源解析把运行配置所有不可用状态合并为 `.invalidRuntime`，未区分损坏、未来版本和文件访问错误。
- `auto_mount.swift:2844` — `installLaunchAgent` 对 `.invalidRuntime` 直接中止；两个来源都不可用时要求用户退出安装后另行初始化。
- `auto_mount.swift:3436` — 已有自测覆盖部分安装来源选择，但未覆盖运行配置损坏时的自动恢复、初始化入口和未来版本保护。

# 根因判断

来源解析只使用存在性和布尔型“可用”结果，丢失了缺失、损坏、未来版本和文件系统错误之间的区别。三个命令没有共同的配置状态模型，也没有统一的备份与恢复步骤。判断置信度：高；现有代码路径和内置测试直接体现了这些行为。

# 修复方案

**首选方案**：为工作区和守护配置实现统一的状态检查与决策函数。损坏的守护配置在工作区配置有效时先生成权限为 `0600` 的时间戳备份，再从工作区原子恢复并继续安装；两边都没有可用配置时，交互式 `--install` 进入向导，配置保存并验证后继续安装。文件访问或备份失败时停止修改。配置版本高于当前程序时单独拒绝自动降级；仅在用户显式选择工作区来源时才允许替换，并备份目标文件。两份配置都有效且内容不同则交互询问，默认保留守护配置；非交互模式也保留守护配置。

`--config` 应管理已安装服务的守护配置；守护文件缺失或损坏而工作区可用时，先安全恢复再进入菜单。没有服务时管理工作区配置；若唯一有效来源是遗留运行配置，可备份工作区无效文件后恢复工作区。无可用来源时进入向导。`--init` 默认不重写已有有效配置；若明确请求重建，则采用显式 `--reset`，并在写入前备份被替换的工作区文件。初始化向导须检查保存结果，且从 `--install` 或 `--config` 调用时不得递归部署。

# 风险与限制

- 配置含 SMB 地址和可能存在的凭据；备份必须保留 `0600` 权限并放在配置同目录。
- 未来版本配置不是损坏文件。自动覆盖可能丢失新版本新增字段或造成守护服务降级，因此默认保留并停止。
- `--init` 默认行为从可能覆盖已有工作区配置改为保留；完整重建必须通过显式 `--reset`。
- 向导依赖交互式终端。非交互安装没有可用配置时必须清楚失败，不得生成伪造或默认业务配置，也不得注册无配置服务。
- 本次验证使用本地状态测试；不触碰 Application Support 真实配置、LaunchAgent 服务或 SMB 挂载。
