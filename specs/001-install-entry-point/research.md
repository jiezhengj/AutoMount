本研究针对 Feature `001-install-entry-point` 的核心技术决策进行调研与论证。

当前代码库基线形态为：源码文件 `auto_mount.swift`、可执行文件 `auto_mount`、守护服务 `com.user.automount`、配置文件 `auto_mount.plist`，GitHub 仓库为 `jiezhengj/AutoMount`。项目历史中存在 `AutoMount`、`auto_mount` 与 `auto-mount` 等多种大小写与分隔符混用的割裂现象。

结合维护者在评估阶段的结论与后续追加的需求，本研究深入论证六项核心技术决策：用户级搬迁式安装、Shell 入口管理、主机可达性探测、网络事件驱动重试、单活动配置自愈机制，以及 CLI 命令简化与项目全局资产统一重命名为 `automnt`。

# 决策一：用户级搬迁式安装与下载副本自清理

### 决策内容

程序采用“自检测 - 搬迁复制 - 权限配置 - 自清理下载副本”的流水线设计：
1. 目标规范安装路径确定为 `~/Library/Application Support/automnt/bin/automnt`（命名依托于决策六）；
2. 运行初期，程序检查当前可执行文件物理路径（通过 `CommandLine.arguments[0]` 与 `proc_pidpath` 获取绝对真实路径）；
3. 若当前路径不等于目标规范安装路径，程序创建目标目录，将自身复制到目标位置，并赋予 `0755` 执行权限；
4. 随后调用 POSIX `unlink()` 解除当前运行位置（原下载副本）的目录项关联，使下载目录不再残留可执行程序。

### 论证与理由

- **POSIX 文件系统语义保障**：在 Darwin / macOS 内核中，对当前正在执行的二进制执行 `unlink` 只会删除目录项索引，文件的 inode 与数据块在该进程内存生命周期内持续有效，直至进程退出后释放，绝不会导致当前进程崩溃。
- **使用者零负担**：使用者在浏览器下载预编译程序后直接在终端运行一次即可，不需要人工搬运到安装目录，也不需要手动返回下载目录清理。
- **纯用户空间安全**：安装位置在 `~/Library/Application Support/` 用户可写空间内，全过程不需要管理员密码，避免长期提权带来的安全隐患。

### 评估与否决的替代方案

- **替代方案 A：就地运行并保留工作区/下载区模式**：否决。这正是导致历史基线版本“两处程序、两处配置、难以确认哪份生效”的混乱根因。
- **替代方案 B：安装到 `/usr/local/bin` 或 `/Applications`**：否决。在现代 macOS 上写入系统级目录需要管理员权限授权，后续自更新与文件替换同样需要提权，与“无感静默更新”和“免反复输密码”冲突。

# 决策二：Shell 命令入口注入与精确还原机制

### 决策内容

1. 安装器检测当前用户环境中的 Shell 配置文件（按顺序检查 `$HOME/.zshrc`、`$HOME/.bash_profile`、`$HOME/.bashrc`）；
2. 注入带有显式防伪定界标记的代码段：
```sh
# >>> automnt CLI begin >>>
export PATH="$HOME/Library/Application Support/automnt/bin:$PATH"
# <<< automnt CLI end <<<
```
3. 注入前先检索是否已存在该定界标记，若存在则更新内部路径，实现写入幂等；
4. 卸载时，精确匹配并删除从 `# >>> automnt CLI begin >>>` 到 `# <<< automnt CLI end <<<` 的整段区间，严格保留用户文件中的其他配置与换行符。

### 论证与理由

- **原生开箱即用**：macOS 默认登录终端即能直接调用简化后的短命令 `automnt`，无需用户手动编辑 profile 或输入冗长的绝对路径。
- **高韧性还原**：显式定界标记能够将工具自身的修改与用户的个性化配置完全隔离，卸载时精准剥离，绝不破坏用户自行设置的别名、环境变量或工具链配置。

### 评估与否决的替代方案

- **替代方案 A：创建软链接到 `~/.local/bin`**：否决。许多普通 macOS 用户的默认 `$PATH` 并未包含 `~/.local/bin`，仍需提示用户修改配置文件，无法达成“装完即可直接运行短命令”的目标。
- **替代方案 B：创建别名 alias automnt=...**：否决。alias 在非交互式脚本或不同子 shell 中的兼容性低于环境变量 PATH。

# 决策三：目标主机可达性探测替代链路层 ARP 识别

### 决策内容

1. 废弃所有针对网关 MAC 地址的解析与匹配逻辑，从代码与配置模型中彻底删除网关 MAC 字段（如 `gateway_mac`）与 ARP 扫描分支；
2. 采用面向网络共享主机的服务可达性探测：使用 POSIX 非阻塞 Socket（`socket(AF_INET, SOCK_STREAM, 0)`）向策略指定的目标主机与端口（默认 SMB 端口 445）发起连接测试；
3. 单次连接探测设置超时阈值（500ms ~ 1000ms），若成功建立 TCP 握手则判定该主机可达；若连接超时或返回不可达错误，则判定为不可达。

### 论证与理由

- **规避系统权限限制**：在 macOS 最新版本上，普通无签名进程由于系统安全与隐私沙盒限制，无法可靠读取物理网关的 ARP 链路层地址，导致依赖网关 MAC 的策略永远无法命中。主机服务端口探测是标准传输层行为，不需要特殊权限或特权签名。
- **精准映射挂载目标**：网络策略的本质是判断“该网络环境下的目标 NAS 或 SMB 服务是否直接可用”，直接探测目标主机的可达性比间接探测网关 MAC 更具代表性，彻底避免因更换路由器导致 MAC 改变而策略失效的问题。

### 评估与否决的替代方案

- **替代方案 A：借助系统工具（如 `arp -a` / `route`）间接提取 MAC**：否决。评估阶段已证明该路径缺少 Apple 官方文档保障，在无 Root 与新系统版本下随时面临失效风险，属于技术债务。
- **替代方案 B：ICMP Ping 探测**：否决。很多 NAS 或企业网关默认禁 ping，且在 macOS 上使用原生 ICMP Socket 需借助外部命令或更高权限，TCP 445 端口直连更能真实反映 SMB 服务就绪状态。

# 决策四：网络配置变化驱动与有限重试循环

### 决策内容

1. 后台 LaunchAgent 服务彻底移除 `StartInterval` 定时轮询机制；
2. 服务触发来源收敛为两类事件：
   - 用户登录会话启动（`RunAtLoad: true`）；
   - 系统网络状态变化（`WatchPaths` 监听 `/Library/Preferences/SystemConfiguration/NetworkInterfaces.plist` 与 `com.apple.airport.preferences.plist`）；
3. 进程被唤醒后执行单次评估流程。为应对 Tailscale、VPN 握手或局域网 Wi-Fi 建立的就绪延迟，对当前优先级最高的策略目标执行有限重试（默认最多重试 3 次，每次重试间隔 1.0 秒，单轮总重试窗口不超过 10 秒）；
4. 顺位策略判断：若最高优先级目标在重试窗口内变为可达，立即挂载并退出；若全部重试耗尽依然不可达，则顺延至下一顺位策略；
5. 所有策略评估完成后，程序立即正常退出，不驻留后台常驻进程。

### 论证与理由

- **彻底杜绝“主动卸载又被挂回”的顽疾**：固定周期定时轮询（例如每 60 秒触发一次）会导致使用者手动卸载网络驱动盘后，下一分钟又被程序静默挂载回来。基于网络配置变化事件驱动，在网络环境未改变的情况下绝不主动二次介入。
- **平滑吸收网络就绪抖动**：网络配置从“断开”变为“连接”时，远端 Tailscale 虚拟网卡往往需要 3~5 秒完成握手，若无重试会导致高顺位策略误判为不可达而错误顺延到备用策略。有限重试（10 秒窗口）能够在短时间内吸收就绪抖动，且不会形成死循环挂起。

### 评估与否决的替代方案

- **替代方案 A：保留 300 秒长周期轮询**：否决。只要存在周期轮询，就无法从根本上消除主动卸载被意外挂回的使用者困扰。
- **替代方案 B：无限等待直到网络就绪**：否决。违反 Constitution 原则 II（不得引入第二个常驻运行进程），若服务一直不就绪会导致进程长期占用内存与系统资源。

# 决策五：单活动配置与自愈机制

### 决策内容

1. 全系统确立唯一的活动配置文件路径：`~/Library/Application Support/automnt/automnt.plist`（命名依托于决策六）；
2. 彻底废弃“工作区配置 vs 运行时配置”的双副本逻辑，程序无论从何处启动，均唯一锁定该活动配置文件；
3. 自愈机制（Self-Healing）：程序每次通过命令行或后台服务启动时，执行轻量级健康自检：
   - 检查安装目录中的二进制是否存在；
   - 检查 Shell profile 中的 PATH 注入标记是否存在；
   - 检查 LaunchAgent 的 plist 注册状态与内容（确保无 `StartInterval`）；
   - 若发现配置或入口异常，优先尝试幂等修复；若遇到外部权限等不可修复情况，向控制台输出可直接复制执行的修复命令。

### 论证与理由

- **落实 Constitution 原则 III**：确保交互命令和后台服务读写的是完全相同的一份物理配置，杜绝配置漂移与同步丢失。
- **防范使用者误操作破坏**：使用者有时会误清理 Shell 配置文件或外部 launchd 任务，自检自愈机制能够让程序在下一次交互中自动恢复健康状态。

### 评估与否决的替代方案

- **替代方案 A：多配置双向同步备份机制**：否决。多副本同步是系统状态不一致的根源，维护复杂度极高且违背单一活动来源原则。

# 决策六：CLI 命令简化与项目全局资产统一重命名为 automnt

### 现状分析与命名问题

当前代码库基线形态存在多重割裂：
1. **命令冗长且不便**：原有命令 `auto_mount` 长达 10 个字符，且中间带有下划线 `_`。在 macOS 标准键盘布局下输入下划线需要按下 Shift 组合键，命令行高频交互成本较高；
2. **多形态割裂认知**：项目历史资产中同时存在大驼峰 `AutoMount`（GitHub 仓库名、文档标题）、下划线 `auto_mount`（CLI 命令、源码 `auto_mount.swift`、配置文件 `auto_mount.plist`）以及部分文档中的中划线 `auto-mount`。新使用者在阅读文档、拉取仓库、配置服务与敲击命令时，容易产生认知混淆与拼写错误；
3. **架构升级契机**：本 Feature 引入“用户级单一副本安装”和“旧版本需卸载后重装新版”的断代分界点，此时是彻底收敛命名、清偿历史债务的最佳工程窗口。

### 决策内容

1. **CLI 命令简化**：
   - 将交互命令缩短为 7 字符纯小写无下划线的 Unix 紧凑风格：`automnt`；
2. **全局资产 1:1 统一命名**：
   - 源码文件重命名为 `automnt.swift`；
   - 编译可执行程序产物为 `automnt`；
   - 唯一活动配置文件命名为 `automnt.plist`；
   - 用户应用支持目录为 `~/Library/Application Support/automnt/`；
   - 日志目录为 `~/Library/Logs/automnt/`；
   - 用户守护服务 Label 统一为 `com.user.automnt`，描述文件为 `~/Library/LaunchAgents/com.user.automnt.plist`；
   - 全仓库公开文档（`README.zh.md`、`README.en.md`、`ARCHITECTURE.zh.md`、`ARCHITECTURE.en.md` 等）及规则文件全量改写为 `automnt`；
   - GitHub 远端仓库名统一改名为 `automnt`（在实施阶段由维护者授权后通过 `gh repo rename` 交付）；
3. **零历史兼容包袱**：
   - 不保留 `auto_mount` 软链接、Shell alias 或代码中的旧名称兼容分支；
   - 彻底清除历史称谓 `auto_mount` 与 `AutoMount`，检索残留为 0。

### 论证与理由

- **命令行输入体验极简**：`automnt` 延续了 Unix 工具经典的去元音或尾部压缩缩写惯例（如 `umount`、`fsck`、`crontab`），单手盲打顺畅，无下划线打断，符合高级 CLI 工具的工程美学。
- **单一真理名称契约**：全项目从仓库地址、文档描述、编译二进制到系统服务、配置目录与日志路径，完全实现 1:1 纯小写单一词汇映射，彻底根除跨组件沟通与维护时的拼写混乱。
- **与旧版本切换策略严格契约对齐**：在需求澄清中，维护者已明确“旧版（2.7.4 形态）使用者先卸载旧版再安装新形态，程序不提供原地兼容逻辑”。因此，不引入任何针对 `auto_mount` 的别名或垫片代码，既避免了多入口导致的测试矩阵膨胀，又保证了新架构代码的结构清晰与可维护性。

### 评估与否决的替代方案

- **替代方案 A：仅创建 `automnt` 软链接别名，内部源码与仓库保持原名**：否决。这种折中方案不仅无法解决名称割裂问题，反而制造了“外部叫 automnt，内部叫 auto_mount，仓库叫 AutoMount”的三重认知混乱，违背“单一真实来源”原则。
- **替代方案 B：双入口并行支持（同时保留 `auto_mount` 与 `automnt` 两个命令）**：否决。在同一个安装目录内维护两个有效可执行文件或在 Shell 中注入两个别名，增加了入口校验与卸载清理的复杂性，且与“旧版彻底卸载重装”的决策相悖。
