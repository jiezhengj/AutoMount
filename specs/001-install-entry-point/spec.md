**Feature Branch**: `001-install-entry-point`

# Clarifications

## Session 2026-10-02（来自评估阶段的已确定决定）

- Q: 安装与升级过程是否允许要求管理员授权？ → A: 允许一次管理员授权（输入一次密码）；但不得要求使用者在每次运行或每次配置时输入密码。
- Q: 是否允许安装器修改使用者的 shell 配置？ → A: 允许，但必须由安装器自行完成，不得要求使用者手工修改；卸载时必须把该修改还原。
- Q: 是否把开发者签名与公证作为方案前提？ → A: 不作为前提，维护者不接受年度签名费用。
- Q: 升级由谁完成？ → A: 由程序自行完成，且使用者机器上不需要任何编译工具。
- Q: “未签名程序读不到网关 MAC”是否纳入范围？ → A: 纳入。本次必须解决该能力问题，或明确给出替代方式与使用者可见后果。
- Q: 安装完成后下载的那份程序由谁清理？ → A: 由安装过程处理，使用者不需要手工清理。
- Q: 如何解决当前系统上读不到网关链路层地址的问题？ → A: 改用“直接探测目标主机是否可达”的方案判定网络，不再依赖链路层地址；相关判据、配置字段与代码整体删除，不保留注释或无用途分支。
- Q: 是否保留固定周期轮询？ → A: 取消固定周期轮询（它会在使用者主动卸载共享后又把共享挂回来）；评估改由登录启动与系统网络配置变化触发，并在同一次触发内对被跳过风险采用有限重试。

## Session 2026-10-02（澄清会话）

- Q: 卸载 automnt 时，配置文件里那些共享目标设置应该怎么处理？ → A: 卸载默认保留配置文件，并提供一条显式的“连同配置一起删除”命令；卸载输出必须提示配置所在位置与彻底清理方式（选定 Option D）。
- Q: 程序在后台自行获取新版本之后，是直接安装，还是需要使用者先确认？ → A: 沿用三档更新策略——默认不检查（关闭）、可选的“仅提示不安装”、可选的“自动安装”；只有使用者显式选择自动安装时程序才自行升级（选定 Option A）。
- Q: 已经装了旧版（2.7.4 形态）的人如何进入新形态？ → A: 不考虑从 2.7.4 原地升级；文档指引使用者先用旧版卸载命令移除旧形态，再按新版步骤安装并重新配置。程序 MUST NOT 为此新增检测、迁移或兼容路径。
- Q: 程序是否需要维护自身安装状态的一致性？ → A: 需要，采用混合方式——每次运行校验安装状态并在不一致时自动修复，无法自动修复时输出一条可执行的修复命令；该能力只面向本版本及以后安装的形态，不承担对 2.7.4 旧形态的修复。

# User Scenarios & Testing

## User Story 1 - 首次安装（Priority: P1）

使用者从发布页下载一个预编译程序并在终端运行它，完成配置与安装。安装结束后：程序只存在于唯一的安装位置，配置也只有那一份，命令入口已经可用，而下载来的那份程序已经由安装过程清理，使用者不需要再手工删除任何东西。

**Why this priority**: 这是本 Feature 存在的理由；如果首次安装结束后仍存在两处可运行程序或两处可编辑配置，问题就没有被解决。

**Independent Test**: 在一台没有开发工具的 macOS 27 Apple silicon 机器上，下载预编译程序、完成安装与配置，然后检查系统中可运行的程序副本数量与可编辑的配置副本数量，并确认下载位置已无残留。

**Acceptance Scenarios**:

1. **Given** 使用者刚下载了预编译程序，**When** 使用者运行它并完成配置，**Then** 配置与安装成功，且安装位置成为程序与配置的唯一活动位置。
2. **Given** 安装已完成，**When** 使用者查看原先下载文件的位置，**Then** 该位置不再留下可运行的程序副本。
3. **Given** 安装已完成，**When** 使用者打开一个新的终端窗口，**Then** 可以用一条简短命令再次进入配置与状态查看，不需要输入完整路径。
4. **Given** 安装过程中任一写入步骤失败，**When** 使用者重新运行安装，**Then** 系统处于可重试的一致状态，不会留下“命令入口存在但程序不可用”之类的半成品。
5. **Given** 使用者机器上没有安装任何编译工具，**When** 使用者完成上述安装，**Then** 全过程不需要编译，也不需要安装开发者工具。

## User Story 2 - 日常运行与再次配置（Priority: P1）

后台服务按登录用户身份常驻，网络配置发生变化时立即触发一次评估；使用者随时可以用命令入口进入配置与状态查看，命令入口与后台服务读写的是同一份配置。

**Why this priority**: 这是“单一活动配置”能否成立的关键——如果两个入口读写不同文件，就退回到本 Feature 要消除的状态。

**Independent Test**: 修改配置后观察后台服务下一轮是否使用新配置；网络配置发生变化时观察是否立即触发评估。

**Acceptance Scenarios**:

1. **Given** 安装已完成，**When** 使用者通过命令入口修改配置，**Then** 后台服务在下一轮使用修改后的配置。
2. **Given** 使用者的网络配置发生变化，**When** 变化发生，**Then** 后台服务在不等待周期轮询的情况下触发一次评估。
3. **Given** 使用者通过命令入口查看状态，**Then** 显示的服务状态与系统实际注册状态一致。

## User Story 3 - 升级（Priority: P1）

程序自行获取新版本并完成替换，过程中不需要使用者机器上的编译工具，升级结束后仍然只有一份程序与一份配置，命令入口无需使用者重新设置。

**Why this priority**: 现有形态的升级要在使用者机器上编译源码，且会把下载区与安装区两边同步；这条是维护者明确要求消除的负担。

**Independent Test**: 在没有开发工具的环境里，从较旧版本升级到新版本，检查升级后程序版本、命令入口可用性与配置保留情况。

**Acceptance Scenarios**:

1. **Given** 使用者机器上没有任何编译工具，**When** 程序执行升级，**Then** 升级成功且不调用编译器。
2. **Given** 升级已完成，**When** 使用者检查系统，**Then** 仍然只有一份程序与一份配置，命令入口保持可用。
3. **Given** 升级过程中失败或被中断，**When** 使用者再次运行程序，**Then** 程序仍可启动并给出可读的结果，不会变成不可运行状态。
4. **Given** 使用者未开启自动安装（默认状态或仅提示），**When** 有可用新版本，**Then** 程序 MUST NOT 自行替换自身；处于“仅提示”时只给出可读提示。
5. **Given** 使用者显式选择自动安装，**When** 有可用新版本，**Then** 程序自行完成升级并保留可查询的失败记录。

## User Story 4 - 卸载（Priority: P2）

使用者执行一条卸载命令即可移除后台服务、命令入口与安装产物；卸载后系统内不再有该服务的注册，也不会留下指向已删除程序的命令入口。

**Why this priority**: 卸载是否干净直接决定使用者敢不敢装；现有形态的卸载已经能移除服务与安装目录，这一行为不应退化。

**Independent Test**: 执行卸载，检查服务注册、命令入口与安装目录三处状态。

**Acceptance Scenarios**:

1. **Given** 安装已完成，**When** 使用者执行卸载，**Then** 后台服务被注销、命令入口被移除、安装产物被清理。
2. **Given** 使用者的 shell 配置在安装后被使用者本人修改过，**When** 使用者执行卸载，**Then** 卸载只移除本 Feature 写入的内容，不破坏使用者其它配置。
3. **Given** 卸载已完成，**When** 使用者在新的终端窗口输入该命令，**Then** 得到“命令不存在”的系统行为，而不是指向失效程序的入口。
4. **Given** 安装已完成且使用者配置过共享目标，**When** 使用者执行卸载，**Then** 程序与命令入口被清理、后台服务被注销，配置文件被保留，且输出中给出配置文件位置与彻底清理的命令。
5. **Given** 使用者选择“连同配置一起删除”，**When** 卸载完成，**Then** 配置文件被移除，且使用者在本 Feature 之外建立的其它配置不受影响。

## User Story 5 - 按主机可达性识别网络（Priority: P1）

程序不再尝试读取当前网络的链路层地址（网关 MAC），而是直接探测策略声明的目标主机的服务是否可达，以此判定当前应使用哪条策略。配置所需的挂载目标来自使用者已经在系统中挂载的共享，或由使用者手工输入。

**Why this priority**: 现有形态在维护者的系统版本上读不到网关链路层地址，导致以该地址为判据的策略永远无法命中；这条不解决，网络识别就始终不可用。

**Independent Test**: 在未使用付费签名、服务以登录用户身份运行的环境里，配置一条指向当前可用主机的策略，观察服务运行后是否命中并完成挂载；同时检查配置中不存在以链路层地址为判据的策略。

**Acceptance Scenarios**:

1. **Given** 使用者已挂载一个 SMB 共享，**When** 使用者运行配置流程，**Then** 配置流程把该共享所在的主机作为探测目标，且不询问网关链路层地址。
2. **Given** 策略声明的目标主机当前可达，**When** 服务运行一次评估，**Then** 该策略命中并完成挂载。
3. **Given** 策略声明的目标主机不可达，**When** 服务运行一次评估，**Then** 该策略不命中，评估继续到下一顺位策略。
4. **Given** 程序未使用付费签名且以普通用户身份运行，**When** 使用者处于已知网络环境，**Then** 网络识别仍然可用。
5. **Given** 配置已经保存，**When** 使用者查看配置，**Then** 其中不存在以链路层地址为判据的策略或相关字段。

## User Story 6 - 从 2.7.4 旧形态切换：卸载后重装（Priority: P3）

已经装过 2.7.4 的使用者按文档先执行旧版的卸载命令，再按新版步骤安装并重新配置。程序本身不为这类切换提供任何检测、迁移或兼容路径；文档必须写清楚步骤与后果（旧配置不会被沿用）。

**Why this priority**: 这类使用者数量很少，且这次切换只会发生一次；为它长期保留代码会变成只在单次升级中有用、之后无人维护的负担。

**Independent Test**: 在一台装有 2.7.4 形态的机器上，按文档执行卸载与重装，确认新形态可用、程序内不存在针对旧形态的专用代码路径。

**Acceptance Scenarios**:

1. **Given** 机器上存在 2.7.4 形态的安装与配置，**When** 使用者按文档先卸载再安装本版本，**Then** 新形态可用，且实现中不存在针对旧形态的检测或迁移代码。
2. **Given** 使用者的旧配置与新格式不同，**When** 使用者完成重装，**Then** 通过新版配置流程重新完成配置，程序不尝试导入旧配置。
3. **Given** 使用者查看安装与升级文档，**Then** 能读到“先卸载旧版、再安装本版、旧配置不会被沿用”的明确步骤与后果说明。

## User Story 7 - 由事件触发的评估与有限重试（Priority: P1）

评估由使用者登录与系统网络配置变化触发，不再按固定周期反复运行。由于网络配置变化发生的一瞬间，高顺位主机可能尚未就绪（例如远程接入需要几十秒完成握手），程序在同一次触发内会对当前顺位主机做有限次数、有限总时长的重试，只有重试全部失败才顺延到下一顺位。

**Why this priority**: 固定周期轮询正是“使用者主动卸载共享后又把它挂回来”的原因；而直接去掉轮询又不加重试，会让高顺位主机因为就绪延迟被跳过、错误地顺延到低顺位主机。

**Independent Test**: 在受控环境下让高顺位主机延迟若干秒才可达，观察服务是否最终命中它而不是顺延；随后手工卸载共享，观察在出现新的网络配置变化之前是否被自动挂回。

**Acceptance Scenarios**:

1. **Given** 使用者的网络配置发生变化，**When** 变化发生，**Then** 服务立即开始一次评估，不等待固定周期。
2. **Given** 当前顺位主机在触发瞬间尚不可达、但在重试窗口内变为可达，**When** 评估进行，**Then** 该策略最终命中，不发生错误顺延。
3. **Given** 当前顺位主机在整个重试窗口内都不可达，**When** 重试结束，**Then** 评估顺延到下一顺位可达策略。
4. **Given** 使用者主动卸载了共享，**When** 没有新的网络配置变化发生，**Then** 程序不会自动把该共享重新挂载。
5. **Given** 重试窗口结束，**When** 本轮评估结束，**Then** 程序退出，不留下常驻等待进程。

## User Story 8 - 安装状态校验与自愈（Priority: P2）

程序在每次运行时校验自己的安装状态：安装位置是否唯一、命令入口是否存在且正确、服务定义是否与当前模型一致。任一不一致时优先自动修复；无法自动修复时，输出一条可以直接执行的修复命令。

**Why this priority**: 使用者会手工删除命令入口、编辑服务描述文件，系统重置或迁移也可能破坏安装状态；没有这项校验，程序会在不被察觉的情况下退化成“服务还在跑、但入口没了”或“周期轮询又回来了”。

**Independent Test**: 在正常安装的机器上分别删除命令入口、破坏服务定义，然后运行程序，观察是否恢复一致或给出可执行命令；同时确认程序不会去处理 2.7.4 旧形态的安装。

**Acceptance Scenarios**:

1. **Given** 使用者删除了命令入口，**When** 程序下一次运行，**Then** 入口被自动恢复；若无法恢复，则输出一条可直接执行的修复命令。
2. **Given** 服务定义被改动成含固定周期触发或结构不符，**When** 程序下一次运行，**Then** 该不一致被检测并修复，或输出可执行的修复命令。
3. **Given** 配置格式经历多次升级，**When** 每次升级完成，**Then** 迁移只作用于唯一活动配置，且迁移前备份数量始终不超过 1 份。
4. **Given** 机器上是 2.7.4 旧形态的安装，**When** 本版本程序运行，**Then** 程序不尝试修复或接管该形态。

## User Story 9 - CLI 命令简化与全局统一命名 automnt (Priority: P1)

使用者在终端中使用简短、紧凑的命令管理网络挂载，不再需要输入带下划线的长命令 `auto_mount`。为消除多重命名并存（`AutoMount`、`auto_mount`、`auto-mount`）导致的心智负担，整个项目的源码文件、编译二进制、配置文件名、守护服务标识、文档与 GitHub 仓库全量统一为 `automnt`，且不保留旧命令的过渡别名（与旧版本先卸载再重装的原则一致）。

**Why this priority**: 命令是使用者最高频交互的入口，7 字符无下划线的 `automnt` 显著降低输入成本；全局命名一致性彻底消除从仓库名、文档到执行命令的认知割裂。

**Independent Test**: 在终端直接输入 `automnt` 能正常运行；检查编译产物、源码、配置文件名、LaunchAgent 描述文件以及 GitHub 仓库名，确认无任何 `auto_mount` 或 `AutoMount` 残留，且输入旧命令 `auto_mount` 得到命令不存在的反馈。

**Acceptance Scenarios**:

1. **Given** 安装已完成，**When** 使用者在终端输入简短命令 `automnt`，**Then** 命令成功执行，响应配置或挂载操作。
2. **Given** 交付完成，**When** 检查仓库结构与元数据，**Then** 源码文件为 `automnt.swift`，可执行二进制为 `automnt`，配置文件为 `automnt.plist`，服务 Label 为 `com.user.automnt`，GitHub 仓库名为 `automnt`。
3. **Given** 使用者在新形态环境下，**When** 尝试输入旧命令 `auto_mount`，**Then** 系统提示命令不存在，程序不维护向后兼容的旧别名或软链接。
4. **Given** 检查全项目公开文档与配置示例，**Then** 不再出现 `auto_mount`、`AutoMount` 或 `auto-mount` 等历史称谓。

## Edge Cases

- 使用者的默认 shell 不是程序默认假设的那一种；命令入口的写入与还原必须仍然正确。
- 使用者重复执行安装，或安装后手工移动、删除过安装目录。
- 安装后使用者又运行了当初下载的那份副本（例如从备份或下载记录中再次打开）。
- 使用者在本 Feature 写入的配置片段之后又手工编辑过同一文件。
- 升级过程中断电、磁盘空间不足或进程被强制结束。
- 配置文件损坏，或配置文件版本高于当前程序版本。
- 系统级的服务注册状态与程序自身记录不一致（服务被外部工具停止或注销）。
- 使用者同时通过命令入口与后台服务访问配置。
- 高顺位主机在触发瞬间尚未就绪（远程接入握手延迟），重试窗口内才变为可达。
- 使用者在一次触发之后主动卸载共享，随后网络配置没有变化。
- 系统从睡眠唤醒但没有产生网络配置变化时的评估行为。
- 重试窗口尚未结束时又发生一次网络配置变化（并发触发）。

# Requirements

## Functional Requirements

- **FR-001**: 安装完成后，系统中 MUST 只有一份可运行的程序副本与一份可编辑的配置副本；程序 MUST NOT 因运行位置不同而读写不同的配置。来源：Spec US1-S1、US2-S1；评估结论 problem.md 目标一。
- **FR-002**: 使用者 MUST 只需下载一个预编译程序并运行一次即可完成配置与安装；安装过程 MUST 处理掉下载来的那份程序副本，使用者 MUST NOT 被要求手工删除它。来源：Spec US1-S1、US1-S2；Session 2026-10-02 已确定决定。
- **FR-003**: 安装后 MUST 提供稳定的命令入口，使使用者能够不输入完整路径地再次进入配置与状态查看。来源：Spec US1-S3；评估结论 problem.md 成功指标。
- **FR-004**: 若命令入口通过修改使用者 shell 配置实现，该写入 MUST 幂等、MUST 由安装器自行完成、MUST NOT 要求使用者手工修改，并且卸载时 MUST 精确还原（包括使用者此后对同一文件的其它修改不被破坏）。来源：Spec US4-S2；Session 2026-10-02 已确定决定。
- **FR-005**: 程序 MUST 提供三档更新策略：默认不检查新版本（关闭）、仅提示不安装、以及自动安装；MUST 只有在使用者显式选择自动安装时才自行升级。任一路径下，升级 MUST NOT 依赖使用者机器上的编译工具，并 MUST 保持单一程序与单一配置、命令入口继续可用；自动安装 MUST 保留失败记录与可见结果。来源：Spec US3-S1、US3-S2、US3-S4；2026-10-02 澄清会话。
- **FR-006**: 安装 MUST 注册以当前登录用户身份运行的后台服务，且该服务 MUST 保留“系统网络配置变化即触发一次评估”的能力，MUST NOT 退化为只有周期轮询。来源：Spec US2-S2；评估结论 research.md 已核实事实。
- **FR-007**: 网络识别 MUST 以“目标主机的服务是否可达”为唯一判据；程序 MUST NOT 尝试读取或匹配链路层地址（网关 MAC）。来源：Spec US5-S1、US5-S2、US5-S5；Session 2026-10-02 已确定决定。
- **FR-008**: 安装、升级与卸载过程中 MUST 允许一次性管理员授权，但 MUST NOT 要求使用者在每次运行或每次配置时输入密码。来源：Session 2026-10-02 已确定决定。
- **FR-009**: 卸载 MUST 注销后台服务、移除命令入口并清理程序安装产物；配置文件 MUST 默认保留，卸载输出 MUST 打印配置文件位置与“连同配置一起删除”的显式命令；程序 MUST 提供该显式删除选项，且删除 MUST 只影响本 Feature 自己的配置，MUST NOT 破坏使用者在本 Feature 之外建立的配置。来源：Spec US4-S1、US4-S4；2026-10-02 澄清会话。
- **FR-010**: 安装、升级或卸载的任一步骤失败时，程序 MUST 回滚到可运行状态并给出使用者可读的结果；MUST NOT 留下“命令入口存在但程序不可用”或半迁移状态。来源：Spec US1-S4、US3-S3、US6-S2。
- **FR-011**: 交互命令与后台服务 MUST 读取同一份活动配置；程序 MUST NOT 长期维护多份可独立编辑并互相同步的配置。来源：项目 Constitution 原则 III；Spec US2-S1。
- **FR-012**: 本 Feature MUST NOT 提供从 2.7.4 旧形态原地升级的路径，MUST NOT 新增针对该形态的检测、迁移或兼容逻辑。安装与升级文档 MUST 指引该类使用者先卸载旧形态、再安装本版本并重新配置，并说明旧配置不会被沿用。来源：Spec US6-S1、US6-S2、US6-S3；2026-10-02 澄清会话。
- **FR-013**: SMB 凭据 MUST 继续由系统钥匙串管理；含内嵌用户名或密码的 SMB 地址 MUST 在保存前被拒绝。来源：项目 Constitution 项目约束（凭据）；现有行为的不退化约束。
- **FR-014**: 安装、升级与卸载 MUST NOT 在使用者机器上编译任何源码，也 MUST NOT 要求安装开发者工具。来源：项目根 AGENTS.md 发布纪律；Session 2026-10-02 已确定决定。
- **FR-015**: README 与架构文档 MUST 描述新的安装、命令入口、升级与卸载流程，且 MUST 使用面向第三方的客观表述，不得包含讨论过程残留。来源：项目 AGENTS.md 文档规范。
- **FR-016**: 本 Feature MUST NOT 改动挂载与卸载的执行规则（共享的挂载、卸载、重复挂载避免）；策略匹配与评估触发机制按 FR-007、FR-017 至 FR-022 调整。来源：评估结论 problem.md 非目标，经维护者 2026-10-02 追加需求修订。
- **FR-017**: 策略配置 MUST 只保留一种匹配判据（探测目标主机）；程序 MUST NOT 生成、接受、解析或输出以链路层地址为判据的策略类型。来源：Spec US5-S5；Session 2026-10-02 已确定决定。
- **FR-018**: 配置流程的挂载目标来源 MUST 只有两种：使用者当前已挂载的 SMB 共享，或使用者手工输入的共享地址；MUST NOT 通过广播、服务发现或网段扫描自动寻找目标主机。来源：Spec US5-S1；Session 2026-10-02 已确定决定。
- **FR-019**: 与链路层地址判据一同废弃的代码、配置字段与交互入口 MUST 整体删除；MUST NOT 以注释、无用途字段、不可达分支或隐藏开关的形式保留。来源：Session 2026-10-02 已确定决定。
- **FR-020**: 评估 MUST 只由使用者登录启动与系统网络配置变化触发；程序 MUST NOT 使用固定周期轮询重新评估。来源：Spec US7-S1、US7-S4；Session 2026-10-02 已确定决定。
- **FR-021**: 在同一次触发内，程序 MUST 对当前顺位主机进行有限次数且有限总时长的重试，只有重试全部失败后才评估下一顺位策略；重试 MUST 有明确上限，MUST NOT 无限重试或留下常驻等待进程。来源：Spec US7-S2、US7-S3、US7-S5。
- **FR-022**: 使用者主动卸载共享后，在没有新的网络配置变化之前，程序 MUST NOT 自动把该共享重新挂载。来源：Spec US7-S4；Session 2026-10-02 已确定决定。
- **FR-023**: 程序 MUST 只有一条配置解析路径：配置位置 MUST NOT 依赖程序从哪个目录启动；MUST NOT 存在“工作区配置 / 运行时配置 / 二者谁优先”这类状态、分支或交互。来源：Spec US1-S1、US2-S1；项目 Constitution 原则 III。
- **FR-024**: 既有的配置格式平滑升级能力 MUST 保留，但 MUST 只作用于唯一活动配置，并在升级前保留迁移前备份；MUST NOT 再遍历多个“可见配置”分别迁移。迁移备份 MUST 最多保留 1 份（保留最近一次），每次成功迁移后 MUST 清理更早的备份，MUST NOT 让备份文件随时间累积。来源：Spec US6-S2、US6-S4；2026-10-02 会话决定。
- **FR-025**: 为实现旧“双副本”模型而存在的解析状态、内容等价性比较、来源选择提示、双写同步与相应内置自测 MUST 整体删除；MUST NOT 以注释、隐藏开关或兼容分支的形式保留。来源：Spec US6-S1；维护者 2026-10-02 对最终代码质量的要求。
- **FR-026**: 最终实现 MUST 以单一模型为唯一结构：MUST NOT 保留被注释掉的实现、不可达分支、隐藏兼容开关，也 MUST NOT 让同一目的的两套路径（旧模型与新模型）并存。该要求适用于整个程序，不限于本规格点名的领域。来源：维护者 2026-10-02 对最终代码“重构级别、干净、优雅”的要求。
- **FR-027**: 程序每次运行 MUST 校验自身安装状态——安装位置唯一、命令入口存在且正确、服务定义与当前模型一致（不含固定周期触发）；不一致时 MUST 自动修复（幂等），无法自动修复时 MUST 输出一条可直接执行的修复命令。该能力 MUST 只面向本版本及以后安装的形态，MUST NOT 承担对 2.7.4 旧形态的修复。来源：Spec US8-S1、US8-S2、US8-S3；2026-10-02 澄清会话。
- **FR-028**: 命令名称与项目全局标识彻底简化并统一为 automnt；本 Feature 交付时，程序命令名（automnt）、可执行文件名（automnt）、配置文件（automnt.plist）、守护服务标识与描述文件（com.user.automnt 及 com.user.automnt.plist）、应用支持目录（~/Library/Application Support/automnt）、日志目录（~/Library/Logs/automnt）、源码文件名（automnt.swift）以及 GitHub 仓库名称全量统一为 automnt；代码、文档与配置中彻底废弃并清除 auto_mount 与 AutoMount 历史称谓。来源：维护者 2026-10-02 追加需求。

## Key Entities

- **安装位置**：程序与配置的唯一活动位置，位于使用者可写范围内，不需要常驻管理员权限。
- **配置**：唯一活动配置，交互命令与后台服务共用。
- **命令入口**：让使用者不输入完整路径即可运行程序的稳定入口，由安装过程建立、由卸载过程移除。
- **下载副本**：使用者最初下载的那份程序，安装完成后不再存在。
- **后台服务**：以登录用户身份注册的服务，具备网络配置变化触发能力。
- **升级来源**：程序自行获取新版本预编译程序的来源（沿用现有发布渠道）。

# Success Criteria

## Measurable Outcomes

- **SC-001**: 安装完成后，系统中可运行的程序副本数量为 1，可编辑的配置副本数量为 1。
- **SC-002**: 安装完成后，原下载位置不再存在可运行的程序副本，且使用者未执行任何手工删除操作。
- **SC-003**: 在一个未安装任何编译工具的环境里，可以完成安装与升级，全程不调用编译器。
- **SC-004**: 卸载完成后，后台服务无注册记录、命令入口不再存在、程序安装产物被清理；配置文件按默认策略被保留，且卸载输出准确给出其位置与彻底清理命令；使用者的其它 shell 配置内容保持不变。
- **SC-005**: 系统网络配置发生变化后，后台服务在周期轮询之前即触发一次评估。
- **SC-006**: 在未使用付费签名且服务以登录用户身份运行的前提下，已知局域网环境中的对应策略能够命中并完成挂载。
- **SC-007**: 本变更进入实施前，评审文档逐条给出使用者可见影响与系统能力影响，并标注“已验证”或“未验证”。
- **SC-008**: 程序生成的配置中，以链路层地址为判据的策略数量为 0，相关字段数量为 0。
- **SC-009**: 在未使用付费签名、服务以登录用户身份运行的前提下，指向当前可达主机的策略能够命中并完成挂载。
- **SC-010**: 后台服务的注册定义中不含固定周期触发；网络配置变化可在周期轮询之外触发一次评估。
- **SC-011**: 使用者主动卸载共享后，在出现新的网络配置变化之前不会被自动重新挂载。
- **SC-012**: 高顺位主机延迟就绪的场景下，程序在重试窗口内命中该主机，不发生错误顺延到低顺位策略。
- **SC-013**: 在默认更新策略下，程序不会自行替换自身；仅在使用者显式选择自动安装后才自行升级。
- **SC-014**: 代码中不存在“按启动位置选择配置来源”的分支，配置解析入口唯一（可通过代码检索与结构检查验证）。
- **SC-015**: 升级路径只写入一处程序与一处配置，升级实现中不存在“工作区副本”相关分支。
- **SC-016**: 连续多次配置格式升级后，安装位置的迁移前备份数量不超过 1 份。
- **SC-017**: 通过代码检索与评审可以确认：不存在被注释掉的实现、不可达的兼容分支，也不存在同一目的的两套并存路径。
- **SC-018**: 在正常安装的机器上删除命令入口或破坏服务定义后，程序下一次运行能恢复一致状态，或输出一条可直接执行的修复命令。
- **SC-019**: 全仓库代码、文件名、构建产物、测试用例、公开技术文档与发布仓库统一改写为 automnt，检索历史称谓（auto_mount、AutoMount）出现次数为 0。

# Assumptions

## Operating Assumptions

- 分发渠道回到项目自身发布页；不在本 Feature 内重新引入包管理器。
- 每次正式版本仍然发布与源码版本一致的预编译程序（现有发布流程已具备该资产）。
- 使用者环境为 macOS 27 及以上的 Apple silicon 设备，与项目支持范围一致。
- 升级在程序一侧完成检查与安装，并保留失败记录与使用者可见的结果提示；确认策略沿用三档策略，仅在显式选择自动安装时执行升级（选定 Option A，见 FR-005）。
- 命令入口的具体写入位置与形式属于实现选择，但必须满足 FR-004 的幂等与还原要求。
- 现有形态中“下载目录与安装目录各有一份配置”的历史状态只影响迁移路径，不影响新安装路径。
- 重试的默认参数取“至少 3 次、间隔约 1 秒、总窗口不超过约 10 秒”，并允许使用者调整；该默认值属于本规格的假设，实施前需由维护者确认或调整。
- 系统网络配置变化是最主要的再评估时机；若系统从睡眠唤醒后没有产生网络配置变化，程序不会自动重新评估，使用者可手工运行一次命令触发（这是取消周期轮询带来的已知代价，需在文档中说明）。
- 网关地址与网卡名称仍可读取并用于诊断输出，但不再参与策略匹配。

## Non-Goals

- 不引入第三方包管理器，也不引入付费签名与公证。
- 不提供从 2.7.4 旧形态原地升级的路径；该类使用者按文档先卸载再重装。
- 不提供可双击安装的安装包形态。
- 不新增常驻的第二个运行进程，不新增图形界面。
- 不改变挂载与卸载的执行规则；策略匹配与评估触发机制按本规格调整。
- 不引入基于链路层地址的网络识别，也不引入基于无线网络名称的网络识别。
- 不改变凭据存储方式。
